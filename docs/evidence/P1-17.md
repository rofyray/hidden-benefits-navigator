## Acceptance evidence

### Six reviewed entries and a pinned manifest

`tests/integration/phase1-gate.test.ts` asserts six entries in `PROGRAM_ORDER`,
six parsed program files, six manifest rows whose `version` matches the program
file and whose `contentHash` is a 64-hex digest, and `manifest.catalogVersion ===
CATALOG_VERSION`.

### No placeholder numbers, no unsourced mandatory paperwork

Every `lte`/`gte` rule carries either a positive `amountCents` or a household
scale whose every entry is positive; every `requiredness: "required"` document
cites at least one evidence id that exists in its program; every rule cites
evidence; every evidence sentence cites a source record that exists.

### Synthetic evaluate → verify round trip

One test evaluates all six programs with a stubbed provider answering exactly the
asked questions (pinned model, zero claim risk), then feeds the minted evaluation
token and drafts built only from catalog evidence into `runVerification`:

- `/api/evaluate` — contract-valid response, `engine: "jev"`, six results.
- `/api/verify` — contract-valid response, six programs, all `status: "approved"`,
  each drafted sentence approved, no `verify.token_unverifiable`.

The synthetic facts are a three-person Texas household with $1,800 gross monthly
income; no real transcript or personal fact is used anywhere.

### D1 and D2 regressions

- D1: for every exclusion-effect rule, `existingLifeline: "yes"` → `fail` with
  `exclusion_applies`; `"no"` → `pass` with `exclusion_does_not_apply`;
  `"unknown"` → `unknown`.
- D2: a single applicant under the individual limits has zero failing criteria,
  a couple under the couple limits likewise, and all four pathway pairs are
  combined under one `any` rule each.

## Resolved decisions

- Exclusion-effect rules are reported as their effect, not as their predicate
  outcome. The catalog states the condition that excludes; screening inverts it.
- Sub-program pathways that differ only by household category are encoded as
  `_ind`/`_couple` composites joined by an `any` rule. A single applicant is never
  measured against a couple's limits.
- A program whose cited sources have unverified effective dates is capped at
  "Possibly" by display policy. That cap is data-driven, not a model judgement.
- The server always recomputes screening from its own catalog; a client-supplied
  label or criterion is rejected by the strict contract.

## Interfaces handed to Phase 2

```ts
// src/server/evaluate.ts
runEvaluation(request: EvaluateRequest, opts: { evaluationDate: string; nowSeconds: number })
  : Promise<{ response: EvaluateResponse; fallbackCode: string | null }>

// src/server/verify.ts
runVerification(request: VerifyRequest, opts: { nowSeconds: number })
  : Promise<{ ok: true; response: VerifyResponse } | { ok: false; status: number; code: string }>

// src/shared/screening.ts
screenProgram({ program, facts, extensions, evaluationDate }): ProgramScreening
RULES_VERSION = "1.1.0"

// src/server/jev/display.ts
labelFor({ screening, covered, staleEvidence, model }): Label
DISPLAY_POLICY = { likelyMinScore: 1.7, likelyMinConfidence: 0.8,
                   contradictionMaxScore: 1.0, lowConfidence: 0.5,
                   maxFollowUpTurns: 3, maxFollowUpsPerTurn: 3 }

// src/shared/catalog
allPrograms() · programById(id) · PROGRAM_ORDER · CATALOG_VERSION · MANIFEST
```

HTTP surface: `POST /api/evaluate` and `POST /api/verify` — same-origin only (403
otherwise), body caps → 413, rate limit → 429/503, strict parse → 400, catalog
mismatch → 409 `catalog_mismatch`, missing/expired token → 409
`reevaluate_required`. Both send `Cache-Control: no-store` and never echo a draft,
token or environment value. `GET /api/public/health` is unauthenticated.

Phase 2 has no unexplained schema or data gap: every contract field consumed by
the UI is produced by one of the two routes above, and the catalog manifest pins
the exact program versions those responses report.

## Limitations carried forward

- `bun run test:eval --live` has never run: it needs the configured provider and
  the hosted `EVALUATION_TOKEN_SECRET`, neither available locally. Release blocker.
- The "Likely" path is still untested on positive cases — five of six programs are
  capped at "Possibly" by unverified source effective dates.
- Four sources remain HTTP 403 or undated: texaslifeline.org and the Texas PUC
  low-income page, the hhs.texas.gov SNAP page, the CEAP income guidelines page,
  and the federal WIC income table (state copy published undated; review due
  2026-12-19).
- Verification checks wording, not eligibility, and the 0.10 unsupported-risk
  ceiling is an engineering starting point, not a calibrated false-accept rate.
- No accuracy claim follows from these synthetic sets; nothing here is calibrated
  to a population.
- The Jev API key was shared in chat and must be rotated before public deployment.
