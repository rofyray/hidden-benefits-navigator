# P1-16 — Evaluate Jev policy on labeled synthetic cases

Date: 2026-09-19. Catalog, rules, question, policy and model versions are recorded
in `docs/evidence/P1-16-report.json` alongside every count below.

## What was built

A labeled evaluation of the display policy and of draft verification, run from one
command, plus the two fixture sets it scores against. Labels are authored from the
catalog evidence and the documented order of reasoning in `src/server/jev/display.ts`.
No model answer was ever recorded and then treated as ground truth.

## Changed paths

- `tests/fixtures/eval-cases.ts` — shared case types, authored model replays
  (supportive / confident-negative / low-confidence / middling), the verification
  case builders, and `KnownDefectId`.
- `tests/fixtures/eval-dev-cases.ts` — 24 development situations, four per program.
- `tests/fixtures/eval-heldout-cases.ts` — 12 held-out situations, two per program,
  never used to choose a threshold.
- `scripts/evaluate-policy.ts` — the runner: mock by default, `--live` requires the
  real provider, `--set=dev|heldout|all`, `--repeat=N`; writes the versioned report
  and separates blocking findings from recorded defects.
- `tests/unit/display-thresholds.test.ts` — threshold boundary regression.
- `package.json` — `test:eval` now runs the evaluation instead of a stub.
- `docs/evidence/P1-16-report.json` — generated report.

## Commands and results

`bun run test:eval --repeat=3` (mock, both sets, three repeats):

- dev: 19/24 labels matched, uncertain share 0.583, 24 verification drafts.
- heldout: 10/12 labels matched, uncertain share 0.833, 18 verification drafts.
- Identical on all three repeats: no run-to-run variance in mock mode.
- **False strong matches: 0** on both sets, all runs.
- **Unsupported drafts approved: 0** on both sets, all runs; also 0 false rejects
  across all 42 verification drafts.
- Exit code 2: the seeded blocking criteria are met, and two recorded defects
  (below) remain open.

`bunx vitest run` — full suite passing, including the 8 new boundary tests.
`bunx tsgo --noEmit` clean. `bun run lint` 0 errors.

## Defects this evaluation surfaced

Both are faults in curated data and screening, not in the labels. The authored
labels were left at the correct answer and tagged, so they keep failing until fixed.

**D1 `exclusion_rule_polarity`.** `rule.lifeline.one_per_household` is declared
`effect: "exclusion"` with `values: ["yes"]` on `existingLifeline`. The screening
engine reports the predicate outcome directly, so the rule *passes* for a person
who already has the benefit and *fails* for a person who does not — and
`labelFor` reads any `fail` as an exclusion. The result inverts the rule:

- `lifeline.snap_enrolled` (no existing Lifeline) → "Not a clear match".
- `lifeline.already_has_benefit` (already has one) → "Possibly", not excluded.

It is the only `effect: "exclusion"` rule in the catalog, which is why nothing
else caught it. The fix belongs to screening: for an exclusion-effect rule the
predicate describes the excluding condition, so a predicate pass must become an
exclusion and a predicate fail must not.

**D2 `medicare_parallel_pathways`.** `medicare_help` encodes individual and couple
sub-program limits as parallel top-level composites (`rule.medicare.msp_qmb_ind`
and `rule.medicare.msp_qmb_couple`, and likewise for SLMB, QI and Extra Help)
with no `any` rule combining them. An individual necessarily fails the couple
composite, and that failure reads as an exclusion, so every single applicant is
shown "Not a clear match" for Medicare cost help. Affects 4 of the 6 Medicare
situations. The fix belongs to the Medicare catalog data: wrap each
individual/couple pair in an `any` rule so the inapplicable branch stops being a
top-level criterion.

## Limitations

- No situation in either set can honestly reach "Likely". Five of the six programs
  carry at least one source whose effective dates are unverified at the evaluation
  date (the open HTTP 403 blockers), and the policy correctly caps those cards at
  "Possibly". The consequence is real: **the strong-match path is untested on
  positive cases**, so the zero-false-strong-match result is a property of the
  current catalog freshness, not evidence that the strong-match rule is safe.
  It must be re-run once those sources are verified.
- Mock mode replays authored answers, so it measures the policy, not the model.
  The three repeats therefore show zero variance; that is not model stability.
- `--live` was not run: it requires the configured provider and the hosted
  `EVALUATION_TOKEN_SECRET`, neither of which exists in this environment. Per the
  release plan this is a **recorded release blocker**, not a pass.
- 24 development and 12 held-out synthetic situations are far too few to support
  any claim about real applicants. Nothing here is a calibration.
- Thresholds were not changed by this evaluation, so "tuned on development data
  only" holds trivially; the held-out set remains unused for tuning.
- A model-version change invalidates this result. The evaluated pin is recorded
  in the report.

## Handoff

`bun run test:eval` is the stable evaluation command. It exits 1 on a blocking
finding (false strong match, unsupported draft approved, or a mismatch with no
recorded cause) and 2 while only recorded defects remain. It will keep exiting 2
until D1 and D2 are fixed; that is the intended signal, and the P1-17 phase gate
should treat both, plus the unrun live evaluation, as open.
