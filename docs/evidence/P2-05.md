# P2-05 — Connect evaluation with revision-safe orchestration

## Changed paths

- `src/client/evaluate/client.ts` — the browser's only path to `POST /api/evaluate`.
  Sends the projected allowlist request, maps every HTTP status to a closed error
  code (`catalog_mismatch` carries the server's catalog version), validates the
  body against `evaluateResponseSchema`, and refuses an answer whose `revision`
  differs from the request's. Retryability is explicit: only `rate_limited`,
  `busy`, `server_error` and `network_error` may be tried again.
- `src/client/evaluate/machine.ts` — `evaluationReducer` plus
  `createEvaluationOrchestrator`. Each submission is tagged with a revision and a
  request id; an answer for an inactive id is counted in `staleDropped` and
  discarded. `invalidate()` aborts the request in flight and clears results, so no
  result can outlive the answers it was computed from. One stage covers the whole
  six-program batch.
- `src/client/evaluate/index.ts` — barrel.
- `src/routes/review.tsx` — wired in: every review action except `confirm`
  invalidates, an answer that changes a fact invalidates, confirm projects and
  submits once, the catalog version now comes from `CATALOG_VERSION` instead of a
  literal, the confirm button is disabled while checking, and a stage line reports
  checking / checked / rules-mode / recoverable failure / catalog mismatch.
- `tests/unit/evaluate-client.test.ts` — 29 tests: batched single request, no
  narrative or span in the body, status→code mapping, catalog version passthrough,
  network failure, contract-invalid body, revision mismatch, abort, rules-mode
  answer, retryability table, reducer stages, stale drop, invalidate, and the
  orchestrator's delayed-answer race, abort-on-edit, reset-after-send and
  subscriber cases.
