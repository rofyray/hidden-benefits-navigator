# P1-14 — `/api/evaluate`

Date: 2026-09-19

## What was built

- `src/shared/catalog/index.ts` (new) — the bundled catalog. Programs and
  sources are imported as modules, not read from disk, because the server runs
  in a bundled edge runtime with no runtime file resolution. Each file is parsed
  with its schema on first access and cached; a malformed catalog fails at the
  first request instead of producing silent gaps. Exports `CATALOG_VERSION`,
  `PROGRAM_ORDER` (also the final ranking tie-break), `allPrograms`,
  `allSources`, `programById`, `catalogIndexOf` and `programHasStaleEvidence`
  (true when the program is past `reviewDueOn` or cites any source that is not
  `verified`).
- `scripts/build-manifest.ts` + `bun run data:manifest` (new) — writes
  `src/shared/catalog/manifest.json`: one catalog version, the rules version,
  the build date, and a SHA-256 of each program file's bytes. Catalog version is
  now `1.0.0` and `data:validate` parses the manifest instead of warning that it
  is absent.
- `src/server/token.ts` (new) — HMAC-SHA-256 evaluation tokens via Web Crypto
  (available in the edge runtime), 15-minute TTL, constant-time signature
  comparison. The payload carries only binding data — revision, catalog and
  rules versions, timestamps, and each program's criterion statuses — so
  `/api/verify` can check the same authoritative screening. No facts, no
  transcript, no identifiers. The secret is read at call time, never at module
  scope; with no secret configured, signing returns `null` rather than issuing
  an unsigned token.
- `src/server/rate-limit.ts` (new) — a per-instance 60-second window of 20
  requests plus a concurrency cap of 4. The caller key is a non-reversible FNV
  hash of the forwarded address, so no address is retained.
- `src/server/evaluate.ts` (new) — the authoritative service. It screens the
  requested programs from the server's own catalog, builds exactly one Jev batch
  from server-authored questions, validates the reply against the asked question
  map, labels and ranks, and signs a token. Any provider problem — not
  configured, rejected credentials, timeout, malformed reply — drops to labeled
  rules mode with `engine: "rules"`, `model: null`, and a closed fallback code.
- `src/routes/api/evaluate.ts` (new) — the thin route: same-origin refusal
  (a cross-origin `Origin` header is rejected before any work; a request with no
  `Origin`, such as a server-to-server call, is allowed), content-length check, the
  request limiter, strict contract parse, catalog-version check, safe error
  codes, `cache-control: no-store`, and content-free logging of route, outcome,
  mode, versions, count, duration and status only.
- `EVALUATION_TOKEN_SECRET` provisioned as a generated 64-character server
  secret; `.env.example` renamed its placeholder to match.

## Acceptance

**Tampered client rules cannot override authoritative sources.** The request
contract accepts facts, program ids, revision and catalog version only. It is a
strict schema, so a body carrying `results`, labels, scores or thresholds is
rejected with `invalid_request` (tested). Every criterion in the response is
recomputed here and carries the server's own `rule.*` catalog ids.

**Limits and catalog mismatch are handled without leaking secrets or bodies.**
Over-size bodies return `payload_too_large` (413) from the declared
content-length before the body is read, and again after reading. A catalog
mismatch returns `catalog_mismatch` (409) with the server's version only.
Rate/concurrency exhaustion returns `rate_limited` (429) / `busy` (503). Every
error body is a fixed code; no request content, environment value or provider
message appears in a response or a log line.

## Verification

`tests/integration/evaluate.test.ts` — 17 tests, all passing: rules mode when
unconfigured; revision and version echo; the tamper rejection plus
server-computed criteria; provider mode with the pinned model asserted on the
outgoing request; fallback on a malformed reply; no retry on 401 (the transport
is called exactly once) with fallback code `invalid_credentials`; one match and
one relevance question per program; dense ranking; all six programs in one batch
with a contract-valid response; rejection of unknown fields, an unknown program
id and a foreign schema version; determinism across two
identical runs; token round-trip, forged/expired/version-mismatch rejection and
the unconfigured-signing case; the rate and concurrency caps and their recovery;
the 32 KiB body cap.

Live check against the running server (`POST /api/evaluate`): 200, `engine:
"jev"`, `model: "jev-1.13.0"`, a signed `v1.` token whose payload decodes to the
four SNAP criterion statuses, and `label: "possibly"`. A malformed body returns
400, a cross-origin request 403, a 40 KB body 413, and a wrong catalog version
409 with `{"error":"catalog_mismatch","catalogVersion":"1.0.0"}` and nothing
else.

Project checks: `bunx tsgo --noEmit` clean; `bun run lint` 0 errors (6
pre-existing shadcn fast-refresh warnings); `bunx vitest run` 316 tests across
16 files; `bun run data:validate` exit 0 — 6 programs, 23 sources, the two
intentional unsupported entries unchanged; `bun run build` succeeds and the
browser bundle contains no credential or provider endpoint.

## Honest limits

- The rate and concurrency limits are per server instance, held in memory. The
  edge runtime may run several instances, so these bound one instance's load;
  they are not a distributed quota and should not be described as one.
- Same-origin enforcement relies on the deployment's own origin handling; no
  CSRF token is issued because the endpoint stores nothing and returns nothing
  identifying.
- `/api/verify` (P1-15) is not built yet, so the signed token is issued but not
  yet redeemed anywhere.
