# P1-12 — Evaluation questions and response validation

Date: 2026-09-19

## What was built

`src/server/jev/policy.ts` (new) — the versioned question builder.
`QUESTION_VERSION` and `POLICY_VERSION` are both `1.0.0`. `evaluationState()`
assembles the batch state: per program, the catalog's rule sentences, the
bounded list of screening checks (`{id, status, rule}` — the deterministic
status computed in code plus one localized rule sentence), the catalog help
description, and the confirmed `need` enum. `evaluationQuestions()` builds one
`score` match question and one `score` relevance question per program on the
authored 0–2 rubrics, plus one `noul` support question per check. Every
instruction is complete on its own, and the only interpolated values are
server-authored IDs — program IDs from the fixed catalog enum and catalog
criterion IDs. Bounds: `MAX_CHECKS_PER_PROGRAM = 8`, `MAX_PROGRAMS_PER_BATCH = 6`,
so the largest batch is 6 × (2 + 8) = 60 questions in one call.

`src/server/jev/validate.ts` (new) — strict validation against the exact
question map that was sent. It requires the pinned model, requires every asked
question to be answered, rejects any answer ID that was not asked, and bounds
each answer by its question type:

- **Noul** — `type: "noul"`, `noul` finite in [0,1]; no `confidence` field is
  expected or read.
- **Score** — `score` finite in `[0, criteria.length - 1]`, `confidence` finite
  in [0,1], optional `legend` must restate the authored criteria by index, and
  `probabilities` must cover exactly the criterion indices, each in [0,1],
  summing to 1 within 0.01.
- **Choice** — `choice` must be an authored criteria key; confidence and
  probabilities as above over the criteria keys.

Failures return a closed reason (`malformed_envelope`, `model_mismatch`,
`missing_answer`, `unexpected_answer`, `malformed_answer`) with the offending
question ID — never a provider message. A malformed answer is never softened
into a low-confidence answer, and a missing answer is never read as neutral.

`tests/fixtures/jev-responses.ts` (new) — six synthetic program states covering
all six catalog programs and every screening status, plus authored confident
negative, confident positive and unsure-positive score answers.

## Answer shape confirmation

One live probe was made on 2026-09-19 against `jev-1.13.0` with a synthetic
three-question state (no personal content). It returned:

```json
{"model":"jev-1.13.0","answers":{
  "m":{"type":"score","score":1.95,"confidence":0.93,
       "legend":{"0":"…","1":"…","2":"…"},
       "probabilities":{"0":0.01,"1":0.03,"2":0.96}},
  "s":{"type":"noul","noul":0.99},
  "c":{"type":"choice","choice":"food","confidence":1.0,
       "probabilities":{"food":1.0,"other":0.0}}}}
```

This confirms the validator's expected fields, including that Noul carries no
confidence, that score probabilities are index-keyed, and that `legend`
restates the authored criteria. The judgments themselves are not used anywhere;
only the shape informed the validator.

## Acceptance

**One call for six programs.** The mocked integration test builds the full
six-program state, sends one `systemOne` request and asserts `fetch` was called
exactly once, with every match and relevance answer validated.

**A high-confidence negative cannot be mistaken for a positive.** Score and
confidence stay separate fields through validation; the test asserts a
`confidence 0.97 / score 0.05` answer validates as a confident answer at the
non-match end of the rubric, with no field that could be read as a match
strength. Turning these into labels is P1-13's gate, not the validator's.

## Honest limits

- The single live probe confirmed response shape only. No live six-program
  evaluation was run; the batch integration is mocked.
- Label assignment, ranking and clarification selection are P1-13 and are not
  implemented here; the validator deliberately stops at a validated answer set.
- The Jev API key was shared in chat and must be rotated before public
  deployment.
