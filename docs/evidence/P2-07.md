# P2-07 — Gate display through server verification

Date: 2026-09-21

## Changed paths

- `src/client/verify/client.ts` — `postVerify`: the browser's only route to
  `POST /api/verify`. One batched call; every HTTP status maps to a closed code;
  the response is validated against `verifyResponseSchema` and refused when it
  answers for another revision. Retryable: `rate_limited`, `busy`,
  `server_error`, `network_error`.
- `src/client/verify/request.ts` — `buildVerifyRequest`: only model-drafted cards
  are submitted; text is sanitized (control characters stripped, whitespace
  collapsed, capped at `LIMITS.maxSentenceChars`); an item whose text still looks
  like a link, phone number or identifier is dropped; the evaluation token is
  passed through exactly as issued. The request is validated before it leaves.
- `src/client/verify/plan.ts` — `assemblePlan`: the gate. A card carries generated
  prose only when the server returned `status: "approved"` and that exact item ID
  is in `approvedSentenceIds` / `approvedChecklistIds`. Anything else — a
  `fallback` verdict, a missing verdict, an approval with no approved sentence, a
  card that was never drafted — becomes a curated card with the reviewed
  `fallbackExplanation` and `fallbackChecklistIds`. Official value text and
  application links are read from the catalog, never from a draft.
  `displayableText(card)` enumerates everything a card may render or speak.
- `src/client/verify/gate.ts` — `gateDrafts`: build → one batched verify → plan.
  Always returns a plan, so a verification failure is never an empty screen.
- `src/client/verify/index.ts` — barrel.
- `src/routes/review.tsx` — after screening succeeds for the current revision, the
  screen composes drafts (only when the on-device model can create a session),
  gates them, and renders **only** the assembled plan. Any review edit clears the
  plan. The plan section renders nothing until `planStage === "done"` and the
  plan's revision matches, so unapproved prose is never in the DOM.
- `tests/unit/verify-gate.test.ts` — 28 labeled tests.

## Acceptance

- *An unsupported explanation or checklist is never seen or spoken.* Unapproved
  text is absent from the plan structure, not merely hidden: `assemblePlan` filters
  by approved ID and replaces a failed card wholesale. Covered by
  "withholds a sentence the server did not approve", "does not speak or show any
  drafted text on a fallback card", and "never leaks drafted prose into a plan
  built from a refused verification".
- *A failed card does not erase approved cards.* Covered by "keeps an approved
  card when another card fails" (approvedCount 1, fallbackCount 1).

## Limitations

- The composition step could not be exercised with a real on-device model: the
  sandbox browser has no Prompt API, so the browser run shows the curated path.
  The approved path is covered by unit tests with synthetic verdicts, and must be
  repeated on the demo device.
- `EVALUATION_TOKEN_SECRET` is absent locally, so a live server verification
  would answer `verify.token_unverifiable` and fall back by design; the client
  handles that as an unapproved card.
- Playback (speech) is a Phase 3 surface. The gate exposes `displayableText` as the
  single source for anything spoken; the voice layer must read only from it.
- The review screen remains a development surface; visual design is Phase 3.

## Synthetic artifacts

All fixtures in `tests/unit/verify-gate.test.ts` are authored by hand: no model
answer is treated as ground truth. The drafted sentences used to prove the gate
("You will definitely be approved.", "Invented promise of $500.") are deliberate
unsupported claims used to assert they never reach displayable text.
