# P1-10 — Build deterministic screening and normalization

Date: 2026-09-19

## Changed paths

- `src/shared/normalization.ts` (new) — period factors, exact annualization, interval
  comparison, basis comparability, catalog field resolution, ISO date range check.
- `src/shared/screening.ts` (new) — four-state rule evaluation over the catalog, exception
  handling, date-based program selection, missing-field and evidence exposure.
- `tests/unit/screening.test.ts` (new) — 115 tests: arithmetic, dates, households,
  exceptions, unknown preservation, and every labeled program fixture run twice.

## What the engine does

**Exact arithmetic.** Nothing divides. Two amounts are compared by scaling both to a common
annual basis with the published periods-per-year factors (weekly 52, biweekly 26,
semimonthly 24, monthly 12, annual 1), so a boundary case cannot drift onto the wrong side
of a published limit. Semimonthly stays distinct from biweekly. A tax-year figure is
annual, and the tax year itself is matched separately: an income rule written for tax year
2025 is `unknown`, not `pass` or `fail`, until the stated tax year matches.

**Four-state logic.** Each rule yields `pass`, `fail`, `unknown` or `notApplicable` with a
reason code, the evidence ids it rests on, and the catalog-authored `blocksLikely` flag —
never a flag inferred at runtime. `all` and `any` combine member statuses with Kleene
logic: one `fail` sinks an `all`, one `pass` carries an `any`, and any remaining `unknown`
keeps the parent `unknown`.

**Exceptions only soften.** A sourced exception can turn a `fail` into `unknown`
(`exception_applies` when the exception passes, `exception_may_apply` when it is itself
unknown). It can never turn a `fail` into a `pass` and never touches a `pass`. This is why
a bare gross-income figure over the SNAP limit does not exclude an older-adult household.

**Unknowns stay unknown.** An unanswered yes/no is `unknown`, not `no`. A missing amount is
`unknown`, not zero — proven by a test that screens the same household with no income and
with a stated $0 and asserts the two statuses differ. An income whose interval straddles a
limit is `unknown`, as is an open-ended interval. Gross income is never measured against a
net or countable limit; the basis must match or the criterion is `unknown`.

**Household definitions are per program.** A threshold table is read with the program's own
household field (`wic.applicableHouseholdSize`, `lifeline.economicHouseholdSize`,
`foodHouseholdSize`), not the common one. Past the largest published size, the table is
extended only by a published per-person increment; where no increment exists (WIC), the
result is `unknown` with `no_published_limit_for_this_household` rather than an
extrapolated number.

**Dates are injected.** `screenProgram` takes an ISO evaluation date; nothing reads the
host clock. Comparisons are string comparisons on ISO calendar dates, so no UTC rollover
can shift a boundary. A program version outside its validity window returns
`applicable: false` with `program_version_not_in_force` and no criteria at all.

**No arbitrary code evaluation.** Rules are data. The evaluator switches on a fixed set of
operators (`enumIn`, `lte`, `gte`, `range`, `all`, `any`, `referral`); a catalog file cannot
introduce behaviour. Unknown rule ids and (despite the validator rejecting them) cycles both
degrade to `unknown` rather than throwing, so evaluation is total.

**Outputs for the client fallback and server recomputation.** Each screening returns the
criterion list in catalog order, the deduplicated `missingFieldIds` that would resolve the
unknowns, the `evidenceIds` the results rest on, and the reason codes.

## Limitations

- Labels, ranking and clarification selection are deliberately not here; they are P1-13.
  This task produces criterion statuses only, so the fixtures' `expectedLabel` values are
  used as a weak consistency check (a "likely" case must have a passing criterion and
  cannot be all failures), not as an assertion of a final label.
- The WIC and Lifeline fixture files record a `pathway` rather than deciding rule ids, so
  the deciding-rule assertion runs against the SNAP, EITC, CEAP and Medicare fixtures and
  is skipped where the fixture does not name rules.
- Programs with alternative pathways (MSP individual vs couple) legitimately report a
  failing sibling criterion; distinguishing "the pathway that does not apply" from "a
  disqualifying result" belongs to labeling in P1-13.
- Extension money bands (`medicare.countableMonthly`, `eitc.agiAnnual`) carry no period or
  basis of their own, so the rule's declared period and basis apply. The catalog gates
  those rules on a separate basis-confirmation criterion; the engine does not infer one.
